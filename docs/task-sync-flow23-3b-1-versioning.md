## Выбор: RPC-only плюс защитные триггеры

| Вариант | Польза | Недостаток |
| --- | --- | --- |
| A: только RPC | единая проверка expected_version и журналирование operation_id | необходим полный отзыв прямого DML; без перехвата каскадное удаление и привилегированный writer нарушают identity |
| B: триггеры, разрешён старый CRUD | любая обычная запись поддерживает version/identity, сохраняет совместимость старого UI на переходе | старый UPDATE без expected_version по-прежнему перезаписывает чужое изменение, а HTTP retry не идемпотентен |

Предлагается сочетание: **триггеры как защита целостности и обработчик каскада, RPC-only как обязательное условие включения sync**. Новый UI до сетевой записи должен фиксировать неизменяемый operation_id/конверт, затем вызывать только RPC. В согласованном maintenance cutover останавливаются старые версии и сторонние writers, отзываются эффективные прямые DML-права у PUBLIC, anon, authenticated и всех унаследованных/колоночных путей; администраторы и BYPASSRLS роли должны быть остановлены или формально встроены в протокол. Нельзя считать React-кнопку барьером. Триггеры не делают старые клиенты безопасными и не заменяют idempotency/version сравнение в RPC.

Изолированный тест демонстрирует остаточный риск: два последовательных legacy UPDATE без version-условия оба проходят, и второй способен перезаписать первый, хотя version увеличивается. Поэтому до завершения cutover синхронизацию запускать нельзя.

## Кандидаты SQL

- [01 storage DRAFT](../supabase/proposals/flow23_3b_01_storage_DRAFT.sql): version и identity backfill под проектируемой блокировкой, приватные таблицы с включённой RLS. Все существующие и NULL-owner задачи сохраняются.
- [04 role DRAFT](../supabase/proposals/flow23_3b_04_role_DRAFT.sql): `flow_task_sync_executor` и отдельная `flow_task_identity_trigger` — NOLOGIN, NOSUPERUSER, NOBYPASSRLS, без доступа членов клиентских ролей. Executor читает identity и журнал, добавляет только свой journal row по RLS, но не изменяет identity; trigger role читает/пишет только identity. Роли не владеют приватными таблицами. Их членство и SET ROLE должны быть запрещены для всех клиентских/внешних ролей.
- [05 triggers DRAFT](../supabase/proposals/flow23_3b_05_task_triggers_DRAFT.sql): `BEFORE INSERT` устанавливает version 1 и резервирует ID; `BEFORE UPDATE` запрещает смену ID/владельца, принудительно увеличивает старую version ровно на 1 и сверяет identity; `BEFORE DELETE` создаёт tombstone version + 1. В случае ошибки вся транзакция откатывается. Триггер с фиксированным search_path и SECURITY DEFINER проверяет TG_RELID, владельца, отсутствие bypass и RLS identity. Решение о запрете переноса владельца должно быть согласовано.
- [03 RPC DRAFT](../supabase/proposals/flow23_3b_03_rpc_DRAFT.sql): сам не изменяет version или identity: он применяет CAS к tasks, trigger выполняет version/identity, RPC проверяет результат прежде чем записать journal. Отсутствие/ошибка триггера приводит к откату. Порядок блокировок: operation advisory → task advisory → строка tasks → чтение identity; прямые DML/каскад захватывают строку tasks до identity. READ COMMITTED обязателен. Возможные deadlock/rollback/retry требуют настоящих многосоединительных тестов.
- [02 cutover DRAFT](../supabase/proposals/flow23_3b_02_cutover_DRAFT.sql): пока не отзывает права и не переключает клиентов. Все файлы намеренно не применимы.

Для глобальной уникальности UUID RPC должен распознавать и чужой UUID, не раскрывая содержимое. Поэтому RLS identity и journal в кандидате даёт **внутренней NOLOGIN RPC-роли** SELECT с `USING (true)`; клиентским ролям нет ни USAGE/SELECT, ни membership/SET ROLE. INSERT журнала проверяет `auth.uid() = user_id`. Аналогичная RLS только для trigger role нужна для nullable владельца и CASCADE без auth.uid. Это не общая политика для authenticated, но функция становится критической границей: она обязана проверять владельца перед выдачей, все вызовы/EXECUTE/owner/наследование необходимо независимо проверить. Роли не используют BYPASSRLS. Не отменять/ослаблять существующие политики tasks.

Управление версиями согласовано только пока триггер включён и не обходится. `session_replication_role`, отключение триггеров, суперпользовательские операции, импорты и другой DDL — отдельные административные пути, которые требуется контролировать. Защита от stale и повторов обеспечивается RPC после закрытия прямого доступа, а не одним ростом version.

## Удаление аккаунта и персональные данные

В PGlite проверено: FK CASCADE вызывает BEFORE DELETE tasks и создаёт tombstone для каждой оставшейся задачи; это согласуется с [описанием PostgreSQL referential actions](https://www.postgresql.org/docs/current/trigger-definition.html). Это не проверка фактической схемы Supabase, system triggers, параллелизма или последствий ошибки триггера при удалении аккаунта. Ошибка сейчас откатывает удаление аккаунта вместе с каскадом; влияние на продукт требует отдельного решения.

Supabase указывает, что уже выданный JWT может оставаться действительным до истечения срока даже после удаления пользователя: [User Management](https://supabase.com/docs/guides/auth/managing-user-data). Кандидат RPC потому проверяет существование `auth.users.id` перед доступом к журналу, повторно после ожидания operation lock и перед записью journal. После **уже закоммиченного физического удаления** synthetic test со старым sub получает 42501 и не получает старый ответ. Никакой Auth grant/policy в DRAFT не применяется: кандидату нужна проверенная `USAGE auth`, `EXECUTE auth.uid()` и **SELECT(id) с RLS-видимостью собственной строки auth.users** для RPC-роли. Реальная возможность, безопасность и политика предоставления таких прав неизвестны; тест даёт SELECT(id) только на синтетической таблице. Без подтверждённого безопасного способа RPC должен оставаться выключенным. Этот SELECT не валидирует отзыв конкретной сессии и не синхронизирует себя с конкурентной транзакцией удаления; вызовы, начавшиеся до commit удаления, требуют независимого решения и тестов. Нельзя считать многократную проверку эквивалентом блокировки/проверки session_id.

Триггер оставляет в identity task UUID, user UUID, version и признак удаления; существующий журнал остаётся с полным payload и результатом, содержащими данные задачи. **Это персональные/псевдонимные данные и новый механизм удержания.** Мы не внедряем очистку, анонимизацию или изменение политики удаления. До развёртывания пользователь/ответственные должны явно согласовать сроки и объём хранения, очистку журнала и tombstones, правовые требования и поведение повторов. UUID сам по себе не анонимен. После очистки журнала идемпотентность старых операций больше не гарантируется без другого механизма запрета/эпохи.

Ещё один подтверждённый на synthetic fixture блокер: если аккаунт с **тем же UUID** будет создан заново, простая проверка существования снова пройдёт и старый неподтверждённый claim сможет получить старый journal result. Это намеренно воспроизведено тестом как известное небезопасное поведение, а требование запрета отмечено TODO. Нельзя предполагать невозможность повторного назначения UUID без проверяемой гарантии или внедрять постоянный account tombstone/новую политику удаления без согласованного решения. Возможное направление — серверная проверка действительной session_id/эпохи аккаунта с тщательно проверенными Auth-политиками и race semantics; она пока не реализована. Поэтому конфиденциальность удалённых аккаунтов **не доказана**, синхронизацию включать нельзя.

## Что проверено и что ещё необходимо

`npm run test:sync-postgres` исполняет кандидаты только внутри одноразовой in-memory базы PGlite. В fixture явно создаётся synthetic `auth.users`, а узкий `SELECT(id)` даётся RPC-роли только в этом тесте. Тест снимает guard только с неизменяемой строки SQL в памяти; DRAFT на диске сохраняет защиту. Проверены: прямые INSERT/UPDATE/DELETE и рост версии; RLS-отказ прямого INSERT и откат резервирования identity; прямой stale UPDATE (воспроизводимый риск); попытка установить version и сменить владельца; RPC create/update/delete и отсутствие двойного увеличения; отказ прямого DML после тестового отзыва grants; проверки владельца и private RLS; идемпотентный повтор, конфликт по версии и запрет повторного ID; synthetic cascade; старый claim после завершённого удаления; атомарный rollback при ошибке журнала. Отдельно тест намеренно демонстрирует сохранение чувствительного journal и повторное открытие при воссоздании того же UUID: это **не пройденная privacy-гарантия**.

Не проверены настоящие PostgreSQL/Supabase/JWT и конкуренция: PGlite не эквивалент Supabase и здесь использует одно соединение. Ранее подготовленный [pgTAP-контракт](../supabase/proposals/tests/flow23_3b_contract_pgtap.sql) требует доработки под trigger role/Auth permissions и полного cutover; не запускался.

Обязательные независимые тесты на двух настоящих PostgreSQL-соединениях в изолированной среде (не production):

1. Барьер после первой блокировки operation_id; второй запрос с тем же ID/тем же payload ждёт, после commit получает ровно тот же результат, после rollback выполняется один раз. С другим payload/пользователем получает общий отказ. Проверить ошибку 40001 и повтор прежнего конверта.
2. Две операции с разными ID и одной ожидаемой version: один commit, второй conflict; сверить один рост version, один финальный snapshot и результаты журнала. Поменять порядок запуска, прервать процесс до/после commit и после отправки ответа.
3. Concurrent прямой UPDATE/DELETE (до отключения legacy) против RPC, одинаковые task IDs, collision advisory hash, `FOR UPDATE` ожидания; затем проверить, что после cutover прямой DML от всех клиентских roles и через наследование/колонки запрещён.
4. Одновременное удаление synthetic auth user через FK и RPC create/update/delete/replay; обоими порядками блокировок, с разрывом сети и deadlock/rollback. Проверить отсутствие ложного tombstone/журнала, запрет старого токена после commit и политику ответа in-flight. Отдельно сценарий отсутствия задач на момент удаления и воспроизведение/запрет повторного UUID после решения по политике.
5. Проверить RLS с настоящими JWT/PostgREST A/B/anon, NULL owner, effective privileges, RLS всех приватных таблиц, PUBLIC/column/default grants и SET ROLE. Роль trigger не должна иметь доступа к journal, authenticated — к приватной схеме/trigger функции. SECURITY DEFINER owner не должен быть postgres/BYPASSRLS.
6. Искусственно вызвать сбой каждого шага триггера и вставки journal, переполнение version, несовместимую RLS и недоступность Auth; проверить атомарный rollback. Убедиться, что удаление аккаунта при ошибке не блокируется незаметно и соответствует утверждённой политике.

## Безопасное развёртывание после отдельного утверждения

Согласовать privacy/retention и решение для повторного UUID и in-flight JWT; проверить Auth role/RLS без автоматического изменения управляемых политик. Собрать все production writers и effective grants, завершить серверные и клиентские реализации и миграцию IDB с сохранением неопределённых/старых операций. Пройти двухсоединительные и Supabase интеграционные тесты, ревью ролей, производительности и резервного копирования. Только затем спланировать maintenance-окно: quiesce старых writers, в **одной** транзакции удерживать блокировку tasks от backfill до установки триггеров/ролей/прав и запрета обхода; подтвердить, что старые клиенты больше не пишут; включать единый RPC только после отдельной проверки. Откат не должен удалять journal/tombstone или разрешать слепой replay. До всех этих условий SQL не применять и sync не включать.
