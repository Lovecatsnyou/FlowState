# FLOW-23.3b.2: удаление аккаунта и защита sync RPC

**Результат: защищённый проект, не готовый к развёртыванию.** Пользователь утвердил логическую политику окончательного удаления: удалить все принадлежащие аккаунту задачи, снимки, payload/результаты журнала, identity и tombstones. Обычное удаление одной задачи сохраняет её tombstone. Кандидаты и тесты ниже не запускают синхронизацию и не изменяют реальный Supabase. Все DRAFT в `supabase/proposals` сохраняют защитные `RAISE` и `ROLLBACK`.

## Очистка и порядок каскадов

В [01 storage DRAFT](../supabase/proposals/flow23_3b_01_storage_DRAFT.sql) `account_lifecycle.user_id` имеет FK `auth.users(id) ON DELETE CASCADE`; identity и журнал привязаны составным FK `(user_id, account_generation)` к lifecycle с CASCADE. `session_gate` привязан и к lifecycle, и к `auth.sessions(id) ON DELETE CASCADE`. Исходный FK `tasks.user_id → auth.users` сохраняется. Физический DELETE пользователя в одной транзакции удаляет относящиеся к нему tasks, lifecycle, session gates, identity/tombstones и полный journal JSONB. Идентичные строки других пользователей остаются. Ошибка в любом cascade/trigger откатывает удаление и всю очистку — тест fixture проверяет rollback.

Порядок FK-каскадов нельзя считать постоянным. В [05 task triggers DRAFT](../supabase/proposals/flow23_3b_05_task_triggers_DRAFT.sql) обычный DELETE задачи создаёт tombstone. Если каскад аккаунта уже удалил identity до trigger задачи, trigger пропускает создание только когда `auth.users` действительно отсутствует; при отсутствии identity у существующего пользователя — ошибка и rollback. Он **не делает вывод об отсутствии**, если на auth.users включена RLS: эта ветка fail closed. Для проверки отсутствия внутренней trigger-роли требуется узкий `SELECT(id)`/USAGE на `auth.users`; DRAFT **не выдаёт** этот грант. Проверить реальные ACL/RLS и разработать безопасный механизм видимости до развёртывания. Не ослаблять RLS Auth ради прохождения тестов. Если безопасность проверки не подтверждена, не устанавливать trigger: иначе удаление аккаунта может ошибочно откатываться или пропустить нарушение целостности.

PGlite проверяет реальный порядок cascade своей synthetic схемы и принудительный порядок с предварительным удалением identity в откатываемой тестовой транзакции. Это не доказывает все порядки system triggers/FK в реальном PostgreSQL и Supabase. FK actions выполняются в транзакции, но конкретные гонки и взаимоблокировки требуют отдельных соединений.

Политика относится к **физическому** DELETE. [Supabase поддерживает и soft-delete](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser), который сохраняет строку Auth; он не запускает эти DELETE CASCADE и пока не соответствует утверждённой очистке. Неизвестно, какие пути удаления используются в проекте и совместимо ли изменение managed Auth; до этого протокол заблокирован. Строки с `user_id IS NULL` не атрибутируются удалённому аккаунту. Логическое DELETE не гарантирует немедленного физического стирания MVCC-страниц, WAL, реплик, logs, audit trail и backups; IndexedDB на других устройствах не очищается само. Для обещания удаления *всех копий* нужно отдельное утверждение и проверка retention/backup/device policy. Никакой бессрочный персонифицированный account-tombstone в схему не добавлен.

## Поколение аккаунта, сессии и operation_id

Сервер создаёт generation аккаунта и session_generation через `GENERATED ALWAYS AS IDENTITY`. Отдельные внутренние NOLOGIN/NOBYPASSRLS роли и RLS-политики создают gate при INSERT в auth.users/auth.sessions; callback [06 Auth gates DRAFT](../supabase/proposals/flow23_3b_06_auth_gates_DRAFT.sql) не прикреплён к реальному Auth. Переназначение `auth.users.id`/`auth.sessions.id,user_id` UPDATE кандидат запрещает; его совместимость с managed Auth не установлена. На физическое удаление FK очищает эти строки. Новые аккаунт и сессия, даже с прежними UUID, получают другие значения; отрицательные тесты включают повторное создание **обоих** UUID.

Проект Custom Access Token Hook, `SECURITY INVOKER`, доступный только `supabase_auth_admin`, добавляет `flowstate_account_generation` и `flowstate_session_generation` в подписанные Auth JWT. Он сохраняет остальные claims и отказывает при отсутствии gate. Подпись, issuer и audience проверяет PostgREST/Supabase; клиентским ролям не даётся EXECUTE hook, прямой SQL-доступ к `auth.users` или `auth.sessions`, membership внутренних ролей, управление GUC и gate. `auth.jwt()` в RPC надёжен только при этой границе. Hook не зарегистрирован; существующие hooks, их совместимость, реальные права `supabase_auth_admin`, доступность поля `session_id` к моменту вызова hook и порядок транзакций login/refresh ещё не проверены. Если hook вызывается до появления доступной строки session_gate, он может блокировать вход — отдельно испытать в локальном Supabase до любого rollout.

Глобальные последовательности generation сохраняют только текущие числовые счётчики, **не сопоставление удалённого пользователя/сессии с поколением**. Это технический минимум для запрета повторного поколения после повторного UUID без бессрочного хранения отдельного account ID. Счётчики также показывают приблизительное количество выдач; влияние на приватность нужно оценить. Запретить их reset/cycle, ограничить владельца и обработать bigint exhaustion. После PITR/restore счётчики могут откатиться назад: без безопасного продвижения и недействительности всех прежних JWT/ключей нельзя снова запускать sync. Тесты in-memory не доказывают безопасность restore.

Протокол **v2** требует неизменяемый account_generation из подписанного JWT в каждом сохранённом сетевом конверте, а также стабильный operation_nonce UUID. Сам `operation_id` — UUIDv8, образованный из первых 122 бит SHA-256 канонической строки `flowstate.task-sync.v2:<generation>:<lowercase nonce>`; сервер пересчитывает его. В новом поколении старые JWT и конверт отвергаются; нельзя просто подставить новое generation и повторить прежний operation_id с прежним nonce. Вероятность SHA-256/122-битной коллизии не нулевая; это криптографическая, не математически абсолютная гарантия. Полный нормализованный JSONB всё равно сравнивается в журнале для обнаружения изменения payload.

После физического удаления журнала сервер **не может узнать**, что произвольно скопированный payload когда-то был другой операцией, если отправитель создал новый корректный v2 ID для нового поколения. Это новая операция; обнаруживать семантическое копирование без хранения связи со старыми данными невозможно. Существующий IndexedDB outbox v2 привязан только к `user_id`, не к account generation: автоматическая перепривязка при том же UUID запрещена. Нужна отдельная миграция IDB, карантин/пользовательское решение для legacy pending/uncertain и сохранение неизменяемого нового конверта до первой сети. Код UI и sync engine не менялись.

## Проверка сессии — намеренно не завершена

RPC проверяет наличие подписанных `sub`, `session_id`, account/session generation, числовой `exp`, совпадение с серверными FK-backed gates, а также exp после ожиданий. Существование пользователя само по себе не считается валидной сессией. Клиентским ролям прямой доступ к Auth-таблицам не открывается; RPC получает данные через приватные gate-таблицы и токен, а task trigger имеет только проектируемый доступ к `auth.users.id` для разрешения порядка удаления.

Однако [Supabase прямо указывает](https://supabase.com/docs/guides/auth/sessions), что наличие `auth.sessions` не подтверждает выполнение timebox/inactivity/single-session политики: очистка может запаздывать и часть ограничений применяется при refresh. Поэтому текущая проверка **не доказывает полную активность сессии** и CHECK readiness не разрешает включить кандидат. Нужно установить реальные настройки Auth и определить/реализовать серверно авторитетную проверку всех применимых ограничений, прав, отзыва и гонок (возможно с отдельным проверенным Auth-сервисом/доказательством), а не объявлять запись sessions достаточной. В проекте также не проверено, удаляются ли реальные session rows при всех вариантах signout/бан/soft-delete. Нет гарантий для ранее начатого запроса, ответ которого уже доставляется в сеть; схема может определить только порядок фиксации транзакций, а не отозвать отправленные байты.

## Гонка RPC против удаления пользователя/сессии

RPC при READ COMMITTED до обращения к журналу берёт `FOR KEY SHARE` на соответствующие `account_lifecycle` и `session_gate`, проверяя обе подписанные generation. Удаление auth.users/auth.sessions обязано удалить эти строки FK CASCADE и взять конфликтующие блокировки. Следовательно, это **не только advisory lock**, который Auth мог бы обойти: если RPC успешно удерживает gate до COMMIT, удаление не должно завершить связанный cascade до освобождения; если удаление зафиксировалось первым, новых gate строк со старой generation нет. При повторном создании с теми же UUID generation меняется. `FOR KEY SHARE` требует UPDATE хотя бы одного столбца; внутренней RPC-роли кандидат выдаёт UPDATE только на `lock_guard`, ограниченный значением true, и RLS по user_id. Auth-таблицы RPC не блокирует и права UPDATE на них не получает. См. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html).

Захват родительских Auth rows, каскадов tasks/session/lifecycle и task/identity locks может идти в другом порядке. Возможен deadlock; PostgreSQL откатит одну транзакцию, но пользовательское удаление может не завершиться. Корректный повтор неизменяемого RPC допустим только при доказанном журнале/активной сессии; процесс удаления должен сообщить об ошибке и не считать её успехом. Блокировки не защищают от администратора, отключившего FK/trigger/RLS, `session_replication_role` или неконтролируемых привилегированных writers. Требуются тесты независимых соединений, управление таймаутами и политика администрирования; PGlite этого не доказывает.

## Проверки и развёртывание

Изменены защищённые DRAFT [storage](../supabase/proposals/flow23_3b_01_storage_DRAFT.sql), [cutover](../supabase/proposals/flow23_3b_02_cutover_DRAFT.sql), [RPC](../supabase/proposals/flow23_3b_03_rpc_DRAFT.sql), [roles/RLS](../supabase/proposals/flow23_3b_04_role_DRAFT.sql), [task triggers](../supabase/proposals/flow23_3b_05_task_triggers_DRAFT.sql), добавлен [Auth gates/hook](../supabase/proposals/flow23_3b_06_auth_gates_DRAFT.sql). Они не являются последовательностью для запуска: настоящий atomic migration ещё не собран. Все новые роли NOLOGIN/NOBYPASSRLS, не владельцы защищённых таблиц; RLS внутренних таблиц включена. Часть политик внутренних ролей допускает SELECT across owners для обнаружения коллизий; их владельцы не должны быть доступны через membership/SET ROLE клиенту, а функции обязаны фильтровать результат. Trigger роли и Auth hook требуют отдельного security review.

`npm run test:sync-postgres` работает только с synthetic PGlite в памяти: логический purge, task tombstone, FK action order, повторный UUID пользователя/сессии, старый JWT и старый v2 envelope/operation_id, чужой аккаунт, RLS/права, JWT exp, повтор операции, version без двойного increment, rollback journal и cascade. Проверяет, что готовность false блокирует RPC; для остальных проверок тест временно меняет только in-memory fixture. Синтетический auth.jwt не проверяет подпись и не проверяет Supabase session policies. Тест не является доказательством реальной безопасности.

Подготовлен [план двух соединений PostgreSQL](../supabase/proposals/tests/flow23_3b_2_concurrency.md), не выполнен: локальные сервер/образ PostgreSQL не обнаружены. Нужны локальный Supabase/PostgreSQL, настоящий PostgREST и synthetic JWT; отдельно проверить PG version и `auth.users`/`auth.sessions` schema, RLS, FK, triggers, grants, `auth.jwt` и Custom Access Token Hook, soft deletion, session revocation и expiry, deadlock/timeout/retry, зафиксированный результат после потери ответа, нулевой остаток пользовательских строк, и backup/restore.

Для ручного ревью подготовлен [read-only preflight Auth metadata](../supabase/proposals/flow23_3b_2_auth_preflight_readonly.sql); он не выполнялся, а определения и ACL могут быть чувствительными. Он не доказывает настройки hooks и effective privileges.

До развёртывания: получить read-only метаданные Auth (без пользователей/токенов), согласовать lifecycle/hook/права и политику всех копий, реализовать настоящую проверку сессий и версионирование IDB, выполнить многосоединительные и Supabase tests, проверить все writers, затем разработать отдельную транзакционную миграцию/backfill/trigger cutover под обслуживанием и отдельным ревью. Ни CHECK readiness, ни DRAFT guards, ни старый CRUD сейчас не переключать.
