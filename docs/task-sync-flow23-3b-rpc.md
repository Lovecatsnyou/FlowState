> Историческое состояние: после добавления кандидата триггеров актуальные выводы и открытые privacy-блокеры см. в [FLOW-23.3b.1](./task-sync-flow23-3b-1-versioning.md).

**Не для production.** Защищённые DRAFT лежат вне автоматических миграций, каждый начинает транзакцию с исключения и заканчивает ROLLBACK. Их нельзя применять или снимать защиту. UI, текущий CRUD, Supabase Auth и outbox не подключены к RPC. Реальная схема и метаданные основаны на сообщении пользователя, а не на нашем соединении с Supabase.

## Подтверждённые метаданные и последствия

Владелец `public.tasks` — postgres; RLS enabled, не forced; четыре политики для authenticated по `auth.uid() = user_id`. `anon`, `authenticated`, `postgres`, `service_role` имеют права на public и прямые SELECT/INSERT/UPDATE/DELETE; первые две роли не BYPASSRLS, две последние BYPASSRLS. В проверенном выводе у `anon`, `authenticated`, `service_role` прямых memberships нет; postgres наследует системные роли. Это не доказывает отсутствие косвенных прав других writers или grants по умолчанию. `tasks.id` UUID PK, `user_id` nullable UUID с FK `auth.users ON DELETE CASCADE`; остальные типы и отсутствие version/пользовательских триггеров описаны в [23.3b](./task-sync-flow23-3b-design.md).

Владелец функции `postgres` опасен: он BYPASSRLS и владеет таблицей. Кандидат проверяет во время вызова, что `current_user` — `flow_task_sync_executor`, роль не superuser/BYPASSRLS, таблица не принадлежит этой роли и RLS включена. При провале — SQLSTATE 42501. Эта проверка **не заменяет** анализ memberships, `SET ROLE`, RLS policies и effective grants; опасная дополнительная привилегия может быть получена другим путём.

## SQL-кандидаты

- [01 storage DRAFT](../supabase/proposals/flow23_3b_01_storage_DRAFT.sql): под lock добавляет version, приватный журнал и identity, backfill включает nullable user_id. Старые DRAFT 23.3a — исторические и не накладываются на 23.3b.
- [03 RPC DRAFT](../supabase/proposals/flow23_3b_03_rpc_DRAFT.sql): конкретный PL/pgSQL `public.apply_task_sync(jsonb)`, защищённый abort/rollback. Нет owner transfer, EXECUTE grant, каскадных триггеров и cutover. Применять нельзя.
- [04 role DRAFT](../supabase/proposals/flow23_3b_04_role_DRAFT.sql): NOLOGIN/NOSUPERUSER/NOBYPASSRLS/NOINHERIT роль, список grants и четыре RLS-политики только для неё. Она не должна владеть tasks или иметь membership у доступной клиенту роли. Не реализован безопасный перенос владельца функции и не разрешён EXECUTE.
- [02 cutover DRAFT](../supabase/proposals/flow23_3b_02_cutover_DRAFT.sql): последовательность переключения без фактического отзыва прав.

Конечная миграция должна в **одной транзакции** создать или обновить функцию, присвоить ей проверенного непривилегированного владельца, отозвать EXECUTE у PUBLIC, anon, authenticated, service_role и всех прочих ролей, получивших его через default ACL, и только затем разрешить вызов нужной authenticated-роли после cutover. Создание функции с владельцем postgres и публичным EXECUTE даже на короткое время недопустимо. Supabase может иметь дополнительные default privileges, поэтому список ролей и ACL требует проверки. `ALTER FUNCTION OWNER` может потребовать права CREATE в целевой schema/специальные административные возможности; нельзя выдавать широкие права постоянно или менять managed Auth для обхода.

## Права исполнителя — кандидат для аудита

| Ресурс | Минимальный предлагаемый доступ |
| --- | --- |
| `public` и `flow_sync_private` | USAGE; не CREATE после установки |
| `public.tasks` | SELECT перечисленных всех текущих полей и version; INSERT только id, user_id и поля payload; UPDATE только поля payload и version; DELETE на таблицу |
| `task_operations` | SELECT, INSERT; без UPDATE/DELETE |
| `task_identity` | SELECT, INSERT; UPDATE только version и deleted; без DELETE |
| `auth.uid()` | уже имеющиеся эффективные USAGE schema auth и EXECUTE функции; если их нет, остановиться и отдельно согласовать решение, не менять Auth автоматически |
| `pg_catalog` | необходимые публичные встроенные функции, включая advisory xact locks |

Дополнительные RLS-политики конкретно для executor используют `auth.uid() = user_id` (USING/WITH CHECK как необходимо). Прежние четыре политики не отключаются и не расширяются для authenticated. RLS executor должен подтверждаться отдельным тестом на живой PostgreSQL: `SECURITY DEFINER`, FORCE RLS=false, владелец объекта и наследование прав могут менять оценку политик. Проверить SELECT privilege для `FOR UPDATE` и `RETURNING`, owner transfer, column grants, default privileges, конкретный PostgreSQL/Supabase version и project role setup. Текущая функция использует `SELECT *`/`RETURNING *`; ACL охватывает все подтверждённые поля, но при добавлении нового поля возможен отказ — это fail-closed, а не гарантия совместимости.

## Реализованное поведение кандидата

Вход ровно из шести ключей: protocol 1, operation_id и task_id UUID, kind create/update/delete, expected_version и payload. Владелец берётся из `auth.uid()`; чужой `user_id`/лишние ключи отвергаются до записи. Version передаётся десятичной строкой без потери точности JS. При update отсутствующее поле не меняется, JSON null устанавливает NULL; payload ограничен шестью полями задачи, типы date/integer валидируются. Максимум 32 KiB текстового JSONB; это кандидатный лимит, требует согласования и ограничения до парсинга на API-уровне.

Запрос нормализует UUID, сохраняет полный JSONB. `pg_advisory_xact_lock` с отдельными namespace для operation и task сериализует выполнение; READ COMMITTED обязателен, другие уровни отклоняются. После блокировки сравнивается полный UUID, owner и JSONB. Идентичный повтор возвращает сохранённый результат; другой payload/owner даёт одинаковый `operation_id_unavailable`. Ошибки валидации не записываются в журнал и не фиксируют применение. Для UPDATE/DELETE проверяются приватный identity, владелец, физическая запись и version; conflict хранится в журнале. Изменение задачи, identity и финального результата журнала выполняется в одной транзакции. При сбое вставки журнала транзакция откатывается. Строка с NULL user_id и чужие/отсутствующие ID возвращают общий отказ без содержимого. Ответ содержит только явный whitelist полей.

UUID задачи глобальный. Уже зарезервированный ID, включая tombstone, не переиспользуется. Отсутствующие до backfill исторические удаления определить невозможно. Данные не передаются в Supabase из UI. Дубликаты входных JSON ключей разрешаются JSON/JSONB парсером до функции; нужно отдельно определить политику на API границе, если требуется запрещать их до нормализации. NULL и отсутствие поля в patch различаются. Каноническая нормализация для date/numeric/Unicode и миграция старых операций должны быть проверены с PostgREST и согласованы до утверждения v1.

### Непосредственный блокер целостности

Сейчас RPC **сам** увеличивает version и поддерживает identity при своих запросах. Он не видит запись, обновлённую существующим прямым CRUD без увеличения версии, и не фиксирует delete через FK `auth.users ON DELETE CASCADE`. После такой потери физической записи кандидат вернёт `rejected/inconsistent`, если владелец ещё может обратиться, но identity остаётся без tombstone. Изолированный тест специально подтверждает это несовершенство. Этот кандидат нельзя включать даже как частичную синхронизацию на живой базе.

Нужны триггеры/альтернативный согласованный механизм для всех INSERT/UPDATE/DELETE и CASCADE; после добавления триггеров нужно переработать RPC, чтобы **не создавать identity и не увеличивать version дважды**, проверить откат/порядок блокировок при конкуренции с каскадом и контролируемым администрированием. Пока `service_role`/postgres/прочие jobs и старые writers способны писать напрямую или обойти RLS, нельзя утверждать, что все изменения проходят через протокол. Административный bypass тоже должен быть остановлен, ограничен или формально включён в протокол. История тombstone и журнал требуют решения по retention/privacy после удаления аккаунта.

## Переключение существующего CRUD

Переход возможен только после проверки всех writers, реализации триггеров, созданного изолированного клиента, который сначала атомарно фиксирует operation ID и полный неизменяемый сетевой конверт, и только потом вызывает один RPC для online/offline. Нужно мигрировать IDB без удаления старых данных, сохранять неопределённые результаты и неподтверждённые ответы, не менять очередь на другой аккаунт. Исторические операции без sequence и старые uncertain нельзя слепо отправлять.

Остановить старые клиенты и интеграции, получить maintenance lock, обеспечить backfill/защиту с начала до конца, выполнить RLS/role/grant audit, в одной управляемой процедуре отозвать все прямые DML от PUBLIC/anon/authenticated и всех эффективных наследуемых/колоночных grants и включить RPC. Новая версия и feature gate должны быть готовы; иначе старый UI перестанет работать. Проверить Dashboard/чтение version и capability policy. При неуспехе rollback транзакции, очередь не очищать. После реального включения откат путём удаления журнала/tombstones или возврата прямого CRUD может повторно применить операции и недопустим без отдельного плана.

## Интеграционные проверки и ограничения

`npm run test:sync-postgres` поднимает **только in-memory PGlite** (PostgreSQL в WebAssembly), создаёт синтетические таблицы/роли и заглушку auth.uid, считывает исходные DRAFT и снимает защиту **только во временной строке в памяти**, не меняя исходные файлы. Он исполняет SQL-кандидат и роль на искусственной схеме, моделирует перенос владельца/revoke/гранты и проверяет RLS, доступ, owner guard, валидацию, повтор, conflict, NULL, rollback task+identity+journal, и выявляет проблему auth cascade. В тестовой схеме пробное отключение RLS — только для проверки fail-closed, не в пользовательском Supabase. PGlite односоединительный: тест не доказывает гонки, настоящее поведение Supabase Auth/PostgREST, политики реального проекта или многопроцессный PostgreSQL.

В [pgTAP-контракте](../supabase/proposals/tests/flow23_3b_contract_pgtap.sql) подготовлены тесты будущего полного cutover, но они не запускались: локальный Supabase/PostgreSQL server и pgTAP здесь отсутствуют. Требуются два независимых PostgreSQL-соединения с барьерами: одновременно один operation_id (идентичный/разный payload), два operation_id одной версии, create vs create, delete/update/cascade, commit/rollback и разрыв после commit, advisory hash collision, deadlock/40001, isolation level, внезапное завершение процесса. Отдельно проверить реальные JWT A/B/anon через PostgREST, прямые grants/колонки/все memberships, function SECURITY DEFINER owner, невыдачу чужих данных, инварианты после ошибок и cascade. Результатом тестов PGlite нельзя подменять эти проверки.

## Что ещё требуется до отдельного ревью миграции

PostgreSQL version; полные RLS definitions, permissive/restrictive режим, владельцы и другие policies; effective ACL в том числе PUBLIC/default/колоночные и SET ROLE paths; какие роли имеют прямой SQL или bypass, их допустимость и интеграции; возможность роли executor использовать `auth.uid()` без изменения управляемой схемы; exposed schemas и ограничения PostgREST/JWT; фактический объём NULL user_id, размер таблицы и maintenance window; транзакционный trigger design для cascade, импортов, перевода владельца и удаления аккаунта; политику хранения/удаления данных; локальную Supabase/PostgreSQL среду с двумя соединениями и pgTAP; safe cutover и протестированный план отката. Никаких real SQL/секретов для этой проверки не использовалось.
