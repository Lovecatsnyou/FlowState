# FLOW-23.3a: проект протокола задач

**Обновление 23.3b:** пользователь сообщил схему `public.tasks` и правила RLS после ручной проверки; совместимость и оставшиеся неизвестные описаны в [новом проекте](./task-sync-flow23-3b-design.md). Следующий аудит ниже фиксирует состояние репозитория на этапе 23.3a.

Статус: **проект для проверки, не протокол в production**. RPC, движок синхронизации, переключение CRUD и готовая миграция не реализованы. Запросы и SQL из `supabase/proposals` не запускаются приложением. Два файла `DRAFT` намеренно прерывают транзакцию. Не применять их к облачной или локальной базе; перед внедрением требуется сопоставить фактическую схему и реализовать недостающие части. Этот документ не доказывает работу PostgreSQL, RLS или сетевого обмена.

## Аудит текущего состояния

- `TaskRow` описывает выбираемые поля `id`, `title`, `subject`, `deadline`, `estimated_minutes`, `priority`, `status`, `created_at`. Для записи также используется `user_id`. Это контракт кода, а не проверенная схема PostgreSQL: типы, ограничения, ключи, триггеры, гранты и наличие других обязательных полей неизвестны. Только миграция `study_preferences` есть в репозитории. Существование или достаточность RLS на `tasks` подтвердить по репозиторию нельзя.
- Список получает серверный компонент после `auth.getUser()`, с фильтром `user_id`. Клиент подписывается на события Auth, очищает отображение при смене пользователя и игнорирует устаревшие результаты. RLS, если правильно настроена на сервере, должна быть самостоятельной границей, а не полагаться на фильтр клиента. IndexedDB и Web Locks не обеспечивают криптографической изоляции и не заменяют Auth/RLS.
- Outbox v2 содержит `operation_id`, `user_id`, `task_id`, `kind`, снимок `task` либо `null` для delete, `created_at`, `state` (`pending`/`uncertain`) и необязательный `sequence`. UI генерирует UUID задачи и каждой операции через `crypto.randomUUID()`. `queueTaskChange` сохраняет задачу/tombstone и операцию в одной IDB-транзакции, новые sequence выдаются в транзакции. У старых записей номера может не быть; timestamps и порядок `getAll()` не доказывают порядок операций. `uncertain` не равен отказу или подтверждению сервера.
- `mergeServerTasks` защищает все task_id с ожидающими операциями; `readTasks` накладывает их видимые локальные снимки на серверный список и скрывает tombstone. Новые записи не удаляют старый кеш, поэтому локальный список может устареть. Локальная очередь не отправляется и не очищается автоматически.
- Онлайн-create/update/delete идут напрямую через Supabase browser client; изменение статуса — через серверную action с повторным `getUser()`. Запросы фильтруются по владельцу, но попытка не имеет durable intent и idempotency key. При потере ответа результат неясен. Локальное изменение серверных задач сейчас заблокировано; задачи с локальным create меняются локально. Эти ограничения сохраняются.

## Контракт операции v1

В качестве входа RPC предлагается один JSON-объект, например:

```json
{"protocol":1,"operation_id":"<uuid>","task_id":"<uuid>","kind":"update","expected_version":"3","payload":{"title":"Новое название"}}
```

Владелец берётся только из `auth.uid()`, клиентский `user_id` в конверте не принимается. `operation_id` — глобальный UUID и первичный ключ журнала; задача и операция используют разные UUID. `kind`: `create`, `update`, `delete`. Для create `expected_version` строго `null`, для update/delete — положительный номер в канонической десятичной строке без ведущих нулей в диапазоне PostgreSQL bigint. Строка не теряет точность JavaScript. Допускаются только явно перечисленные поля задачи и типы, различаются отсутствующее поле и JSON null; `user_id`, `version`, `created_at`, локальные метаданные и лишние поля запрещены. Delete имеет `payload: null`; create и update — объект с оговорёнными полями. Необходимые ограничения полей установить после инвентаризации существующей схемы.

Сервер валидирует и нормализует все значения, строит неизменяемый канонический JSONB из `protocol`, `task_id`, `kind`, `expected_version`, `payload` и связывает его с `auth.uid()` и `operation_id`. Для строгой проверки повтора сравниваются **полные JSONB-значения и владелец**, а не только хеш. Порядок ключей объекта не имеет значения; правила null/отсутствия, чисел, дат и допустимых полей задаются сервером и версией контракта. Хеш не нужен для идентичности и может применяться лишь для диагностики/индексации с проверкой полного значения. Самостоятельная сериализация JS не является эталоном JSONB.

Результат также записывается целиком: `{protocol, operation_id, task_id, outcome, version, task}`. `outcome` — `applied`, `conflict` или `rejected`; `task` содержит разрешённый владельцу серверный снимок либо `null`, для tombstone — отдельный признак `deleted` и последнюю версию. Конкретный список безопасных полей снимка фиксируется после аудита схемы. Повтор идентичного вызова возвращает **сохранённый первоначальный результат**, даже если задача уже снова изменилась. Та же операция с другим содержимым/пользователем получает обобщённый отказ без раскрытия чужой записи; журнал не меняется. На результат с чужим task_id возвращать одинаковый отказ для отсутствующей и чужой задачи, включая tombstone. Новую попытку после конфликта оформлять новым operation_id и новым согласованным ожидаемым version.

## Транзакция и гонки

Для каждой RPC вся проверка, изменение `tasks`, tombstone и запись результата журнала находятся в **одной транзакции PostgreSQL**. Одна из возможных реализаций при `READ COMMITTED`:

1. Проверить `auth.uid()`, формат и размер конверта. Взять транзакционную advisory-блокировку по operation_id в отдельном пространстве имён. Хеш блокировки допустим: коллизия только сериализует независимые запросы, но никогда не заменяет проверку UUID. Использовать разные пространства ключей для операции и задачи, одинаковый порядок захвата; таймауты/квоты ограничивают злоупотребление.
2. После блокировки **отдельным SQL-оператором** прочитать журнал по полному UUID, сравнить владельца и канонический запрос, вернуть сохранённый результат при совпадении. Два конкурентных одинаковых запроса ждут друг друга; после commit второй видит журнал, после rollback — выполняет операцию сам. При deadlock/serialization failure вся транзакция откатывается; клиент повторяет только тот же неизменённый конверт.
3. Для нового operation_id взять транзакционную блокировку по task_id, охватывающую и отсутствие физической строки; затем перечитать identity/tombstone и `tasks`. При реализации с уникальным INSERT вместо advisory lock учитывать, что `INSERT ... ON CONFLICT DO NOTHING` при READ COMMITTED может столкнуться с невидимой в снимке строкой: читать результат следующим оператором, а не предполагать его наличие в том же снимке.
4. Проверить владение и version. Применить одну операцию либо зафиксировать разрешённый структурированный конфликт. Записать окончательные request и result в журнал и завершить транзакцию. Не отправлять клиенту подтверждение до commit. Любое исключение откатывает и задачу, и журнал. Для `REPEATABLE READ`/`SERIALIZABLE` отдельно проверить повторные снимки и SQLSTATE 40001; модель выше рассчитана на `READ COMMITTED`.

Версионирование: все существующие задачи получают начальное `version = 1`; каждое изменение, включая смену статуса, увеличивает его ровно на единицу. Доступное значение версии является **серверным**, а не вычисленным клиентом временем. Для update/delete сравниваются `expected_version` и текущая версия под блокировкой; несовпадение возвращает сохранённый `conflict` без изменения задачи. Физический delete может удалять строку только вместе с атомарным сохранением identity/tombstone владельца и последней версии (удаление само увеличивает версию). Удалённый ID больше не используется для create. Если задача уже удалена, даже при совпадении старой версии возвращать конфликт `deleted`, не считать чужое удаление подтверждением именно этой операции. Исторические удаления, произведённые до появления tombstone, неразличимы от несуществующих; для них возвращается общий `not_found_or_forbidden`, без предположений о последней версии.

Текущие серверные записи могут изменяться через старые браузеры и прочих клиентов. До отключения этих путей даже корректный RPC не обеспечивает контроль версий. Backfill identity, обновление version и фиксацию tombstone при всех старых изменениях следует спроектировать по реальным ограничениям, не допуская окна между backfill и включением перехвата, а затем проверить гонками. Триггеры не заменяют ограничения прав и не гарантируют идемпотентность старого CRUD. Включение sync и работа старых writers одновременно **запрещены**.

## Права и RLS

Предпочтителен `SECURITY INVOKER`, но для защищённого журнала одного invoker недостаточно: если дать `authenticated` прямые права вставки/чтения журнала, клиент сможет подделать подтверждение или запросить чужие результаты, а если оставить прямые права записи в tasks — обойти RPC. Поэтому рассматривается небольшой `SECURITY DEFINER` с отдельным `NOLOGIN NOBYPASSRLS` владельцем, без membership у клиентских ролей, с минимальными правами на нужные столбцы и приватные таблицы. Нужно отдельно проверить, что этот владелец **не владелец tasks**, не суперпользователь, не имеет BYPASSRLS и не получает их через наследование; для него нужны узкие RLS-политики на `tasks` по `(select auth.uid()) = user_id` для соответствующих команд. Действующие политики не ослаблять. Исполнитель всё равно явно проверяет непустой `auth.uid()` и владельца каждой затронутой записи/журнала; права и RLS проверяют оборону независимо. Нужна отдельная оценка GRANT/REVOKE, политики SELECT для UPDATE, владельца приватных таблиц и поведения при `FORCE ROW LEVEL SECURITY`.

RPC: `SET search_path = ''`, полная квалификация таблиц/функций, без динамического SQL из входа; REVOKE EXECUTE от PUBLIC и anon, проверить прямые/унаследованные grants, разрешить только authenticated. Приватная схема не должна быть exposed в PostgREST; схемные и табличные права отозвать у PUBLIC/anon/authenticated, в том числе через наследование и default privileges. Отдельно проверить, что роль функции не может изменять произвольные таблицы или назначать себе права. `auth.uid()` доверять только внутри проверенной серверной сессии. Ни service-role, ни secret key в браузере недопустимы.

## Жизненный цикл клиента и outbox

Проектируемые состояния: `pending` (ещё не зафиксирован полный сетевой конверт), `sending` (конверт и attempt сохранены до сети), `uncertain` (ответ потерян), `acknowledged`, `conflict`, `permanent_error`. Разрешено `pending → sending → acknowledged|uncertain|conflict|permanent_error`; `sending` после закрытия вкладки/падения становится `uncertain`. Из `uncertain` — только повтор **того же сохранённого конверта и ID** после включения проверенного серверного протокола или ручное разрешение; таймаут не доказывает неприменение. Транспортная ошибка не удаляет запись. `conflict` и `permanent_error` блокируют дальнейшие операции этой задачи; разрешение создаёт новую операцию, не переписывая старую. Классификация ошибочных ответов должна учитывать, что аутентификация, неясные HTTP ошибки и crash не подтверждают отсутствие commit.

Существующий outbox хранит полные локальные снимки, а не готовые RPC-конверты. Будущий адаптер должен прочитать неизменяемый снимок именно данной операции, проверить владельца и создать payload только из разрешённых серверных полей; `user_id`, `created_at` и локальные метаданные исключаются. Для update нужна отдельно проверенная семантика полного или частичного изменения, чтобы не затереть чужие поля; сам факт наличия снимка не разрешает принудительное обновление устаревшей версии. Delete строится из task_id и полученной базовой версии, а не из отсутствия записи в кеше.

Операции одной задачи отправляются строго по устойчивому локальному порядку, только после подтверждения предыдущей. Для локальной последовательности create → update → delete серверные версии второго и третьего запросов неизвестны заранее: движок после каждого подтверждения атомарно формирует и **сохраняет неизменяемый полный конверт следующей операции с полученной версией до первого сетевого запроса**. Нельзя вычислять expected_version заново при повторе. Операции разных задач могут выполняться независимо после проверки ограничений конкурентности. Хранить попытку, готовый конверт и результат в новой версионированной схеме IndexedDB без разрушительной миграции. `sequence` отсутствует у части старых операций: при неоднозначном порядке не угадывать по времени и UUID, оставить их нетронутыми и заблокировать отправку до отдельного разрешения. Старые `uncertain` без серверного протокола тоже не повторять автоматически.

Движок и весь CRUD используют единые блокировки пользователя/задачи между вкладками; Web Locks координирует только один браузерный профиль, а PostgreSQL — все устройства. Сетевой запрос не удерживает IDB-транзакцию. До отправки запись `sending` и полный конверт фиксируются атомарно; подтверждение атомарно обновляет **только соответствующий operation_id**, базовую версию и состояние. Если после отправки добавлены новые локальные изменения, не заменять ими текущий локальный снимок серверным ответом и не удалять более новые операции. При сбое транзакции подтверждения сохранить очередь: после перезапуска повтор того же ID получит записанный сервером результат. Порядок удаления подтверждённых записей/аудит и логику сохранения следующей операции нужно отдельно проверить на сбоях между всеми шагами.

При logout/account switch остановить новые отправки и не применять ответ к состоянию другого пользователя. Уже ушедший запрос нельзя считать отменённым: сервер может его зафиксировать. Его исход остаётся `uncertain` для исходного владельца; при следующем подтверждённом входе именно этого пользователя можно безопасно повторить неизменённый конверт после готовности RPC. Auth недоступна — не открывать произвольный кеш и не отправлять данные. Полноценная офлайн-авторизация не входит в проект.

## Развёртывание, проверка и откат

1. Вручную провести **только read-only** инвентаризацию схемы SQL из `flow23_3a_00_preflight_readonly.sql` и отдельно проверить функции/roles, membership, принятые политики и права по владельцам. Не передавать секреты или содержимое задач. Сделать резервную копию и план обслуживания. `DRAFT` не готовы и автоматически не применяются.
2. На отдельной локальной Supabase/PostgreSQL-среде воссоздать проверенную схему и RLS без пользовательских данных; спроектировать полную additive миграцию с безоконным backfill/триггерами, RPC и узкой ролью. Протестировать её и производительность, затем отдельно проверить регрессии текущих клиентов. До cutover sync остаётся выключенной.
3. Подготовить новый клиент, в котором **все** изменения, онлайн и офлайн, сначала фиксируют намерение и используют один RPC. Инвалидация/refresh Dashboard остаются отдельной задачей интеграции; все читающие пути должны понимать версии и удаления. Добавить feature gate и отключить несовместимые старые версии/прочих writers. В одной контролируемой процедуре убрать прямые права всех эффективных клиентских ролей и включить новый путь; возможна пауза записи. Старый UI после отзыва права сломается, поэтому нельзя включать это на текущем этапе.
4. После будущего тестового развёртывания: проверить metadata, RLS и effective grants; от отдельных сессий A/B/anon и отдельными соединениями проверить чтение/запись/повторы, отсутствие доступа к журналу, историю tombstone, перезапуск после потери ответа, результаты Dashboard и политику старых клиентов. Не тестировать изменениями реальных задач. Только после этого согласовывать rollout.

Откат не может просто удалить журнал, tombstone или версии: это разрушит идемпотентность старых повторов и позволит повторное применение. После включения протокола хранить журнал и tombstone бессрочно, пока не определена безопасная политика удержания с учётом срока жизни всех устройств и обязательств удаления персональных данных. При откате сначала остановить всех writers/отправку, сохранить данные и журнал, проверить совместимость и согласовать миграцию состояний. Старый прямой CRUD не является безопасным откатом без изменения модели. Браузер может очистить IndexedDB: гарантия сохранения локальных данных ограничена успешным commit и сохранностью профиля/хранилища; резервирование локальной очереди и политика приватности требуют отдельного решения.

## Проверки будущей реализации

`tests/sync-protocol-model.test.mjs` — исключительно исполняемая **модель**: она не вызывает PostgreSQL, RPC, RLS, Supabase или реальный sync engine и не подтверждает безопасность production. Будущие обязательные интеграционные проверки: две транзакции/соединения с одинаковым ID и разным payload (commit/rollback, паузы после захвата блокировок), два обновления одной версии, одновременный create/delete, повторы после обрыва ответа до/после commit, полный перечень прав через inherited роли, SELECT/INSERT/UPDATE/DELETE от A/B/anon, вызов RPC с чужими ID и отсутствие утечек через конфликты, неизменность журнала, rollback при всех исключениях, старый CRUD после cutover, миграция существующих/legacy-операций и crash в каждом шаге IDB.

Для локальной среды установить Supabase CLI и Docker, создать отдельный тестовый каталог и synthetic schema/users, запустить `supabase start`, затем `supabase test db` для pgTAP-тестов. Не использовать `--linked` и не выполнять `db reset` в существующем или облачном проекте. Для реальных гонок дополнительно нужны два независимых подключения и управляемые барьеры: один pgTAP-тест в транзакции сам по себе не доказывает межсоединительную конкурентность. Команды, секреты и сетевые обращения к пользовательскому Supabase на этапе 23.3a не выполнялись.
